# 正式领取轮次：验证边界

当前仍未确认可用于自动排序的实际领取信号。三卡推荐继续采用整体统计；分阶段统计只供手动参考。诊断页面的场景选择不改变轮次，也不改变推荐。

## 为什么不能直接计数

等级只适合控制识别准备时机，不代表已经领取。候选卡弹出、刷新、拥有强化数量以及强化相关事件数量，都不能区分正式选择、属性碎片、锻造器或特殊强化带来的额外选择。

官方 [Game Client API](https://developer.riotgames.com/docs/lol#game-client-api) 提供本人状态、事件和接口描述，但公开示例不构成当前国服正式领取序号的证据。[ARAMKit 阶段说明](https://aramkit.com/en-US/blog/augment-rarity-and-stages) 可用于理解统计口径，不能代替本机领取事件。

## 本次实现

- 仅手动检查固定的三个本地只读接口；维持 30 秒冷却、单次请求合并、响应体和超时上限，不增加后台轮询。
- 只保留字段类型、有限数值及数量，不保留账号、英雄身份、强化 ID、字符串值或原始响应。
- 可在操作前后各检查一次；最多在当前页面内存保留两份脱敏观察，不写盘、不上传。
- 使用已有 LCU 状态的会话修订号隔离观察；认证变化、游戏阶段变化或连接关闭都会改变修订号。只读缓存，不额外请求 LCU。
- 两次观察超过两分钟、跨会话、接口失败或截断时，拒绝对照。相同会话只能说明观察可比较，不等于领取语义已验证。
- 清空对照或切换场景后，迟到的请求结果不能恢复旧记录。

## 必须完成的实战验收

| 场景 | 将来可信信号必须满足的结果 |
| --- | --- |
| 正式四次选择 | 确认属于本人、本局、正式奖励，选择成功后才更新已领取状态 |
| 连续刷新 | 候选内容可变，正式领取次数不变 |
| 属性碎片 | 不计入正式四次选择 |
| 多个锻造器连续弹出 | 不递增正式次数，不借用随后正式选择的统计阶段 |
| 特殊强化带来的额外选择 | 与正式奖励明确区分 |
| 碎片先于等级奖励弹出 | 先排除碎片，直到正式奖励身份可验证才使用阶段统计 |
| 重连、结束后新对局 | 清除旧局证据；无法重建可信领取状态时回退整体统计 |

需要验证“已领取次数”和“当前待选正式轮次”的差异，禁止仅用已领取数加一来推测任意弹窗。任何新的适配器都必须有上述真实脱敏样本及回归测试后才能开启自动阶段排序。

2026-10-11 本机只读检查时游戏和客户端未运行，三个接口不可访问，因此本次没有实战领取确认结果。自动阶段排序仍关闭。

## 界面预览

`node scripts/preview-workbench.mjs` 使用隔离、隐藏的 Electron 窗口和虚构数据，阻止 HTTP 请求，不连接游戏或真实用户配置。输出位于忽略的 `build/workbench-preview/`。预览数值不是性能实测。

主界面使用静态 SVG 和 CSS，不增加动画、截图或识别任务。`node scripts/build-brand-icon.mjs` 从原创 SVG 生成窗口/托盘/安装包图标。
