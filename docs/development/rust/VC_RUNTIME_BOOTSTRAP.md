## 最低版本的依据

`rust/vc-runtime-policy.json` 记录 x64 **项目支持基线 14.51.36247.0**，
不是声称这是所有二进制在 ABI 上能运行的最早版本，也不是开发机已经安装的版本。

- 本机实际读取的 `cl.exe` 为 `19.44.35229.0`、`link.exe` 为 `14.44.35229.0`。
  目录名 `14.44.35207` 不能代替文件版本；本机系统 DLL 的 `14.50.35719.0`
  也不能证明所有新构建的最低要求。
- 微软要求运行库至少覆盖所用工具链，并匹配程序架构；ONNX Runtime 的 Windows
  要求 VC++ 2019 运行库并推荐最新版本。此处采用更保守的已核对支持基线。
  来源：[微软 VC++ 要求](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist)、
  [ONNX Runtime 安装要求](https://onnxruntime.ai/docs/install/)。
- 从微软官方下载的 `VC_redist.x64.exe` 为 `14.51.36247.0`，签名有效、签名者为
  Microsoft Corporation，SHA-256 为
  `843068991daaa1f73ad9f6239bce4d0f6a07a51f18c37ea2a867e9beca71295c`。
  仅在隔离目录静态解出 CAB，未执行 EXE 或 MSI；其中 7 个受检 x64 CRT DLL
  的 FileVersion 都为 `14.51.36247.0`，所以没有把安装器版本直接当成 DLL 版本。
- 同时固定 ONNX Runtime `1.26.0` 与 4 个随包第三方 DLL 的 SHA-256。
  更换这些 DLL、依赖版本或使用更高版本编译器时，必须重新核对基线，不能沿用旧声明。

后续构建使用 `scripts/build-rust-with-evidence.ps1`：读取实际 MSVC 编译器和链接器
文件版本，明确设置 C/C++ 编译器与 Rust 链接器路径，检查与支持基线的关系，使用工具链 /
策略身份隔离 Cargo 元数据，然后编译核心和选定前端。脚本不打包、不运行 FUZE。
源码相关目录须已提交；原有本机交接笔记不在构建检查范围，不会被覆盖或暂存。

全部编译成功且源码身份未变化后，写入 `release/fuze-build-evidence.json`：
提交、前端、工具链版本、策略散列和本次 EXE 散列。开始构建时使旧回执失效。
这是未来阶段构建的入口；本轮没有用历史二进制伪造一次新构建回执。

打包器在自检和生成 ZIP 前验证回执与实际复制的二进制，枚举普通和延迟 PE 导入，
将受限 `vcRuntime` 对象写入 `build.json`。缺少回执、散列不匹配、架构错误、
新的 CRT 依赖或工具链超出基线都会阻止新包生成。
`build.json.runtime` 继续表示 ONNX 版本，不改字段语义。
旧 build.json 缺少 vcRuntime 时保持未知，不回填本机、导出器或最新工具链版本。

## 安装入口与兼容范围

原始 ZIP 的 `Install-local.cmd` 先调用 `Install-local.ps1`，在任何 FUZE EXE
运行前读取构建记录、校验载荷散列、检查系统目录中所需 VC DLL 的存在、x64 架构和版本。
较新运行库直接跳过引导；缺失、过旧或错误架构时给出固定微软下载地址和本地安装器路径输入。

不自动下载。只有玩家明确输入 `INSTALL` 后，才会验证所选安装器的固定散列、微软签名、
版本并请求 UAC，使用 `/install /passive /norestart`。用户拒绝、UAC 取消、安装失败、
安装返回 0 但依赖复检仍失败，都不会启动 FUZE 安装。
3010 / 1641 提示用户安排重启并重新运行入口，不继续安装或自动重启；1638 也必须复检。
通过检查后才进入原有 `fuze-update --install-local` 确认 / 安装流程，不另写安装器。
退出码参考：[微软分发及安装选项](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files)。

`Install-local.ps1 -CheckOnly` 只读检查并输出有限状态，不提示输入、不下载、不提权、
不安装运行库或 FUZE。0 表示依赖检查通过，2 表示缺失 / 版本未知，1 表示输入 / 校验失败。
这不是运行时加载或完整安装成功证据。

PS1 仅进入 ZIP，不进入 FUZ，也不扩大旧原生更新器的根文件白名单。
受管目录没有这个 helper 时，Install-local.cmd 明确要求回到原始 ZIP，不绕过检查运行 EXE。
2026-10-20 的后续源码将 `Start-this-build.cmd` 接入同一引导，检查通过后才启动
当前 ZIP 指定的 Slint / Win32 前端，不读取受管版本指针；入口不再带执行策略绕过参数。
`-CheckOnly -LaunchThisBuild` 仍只读，不会启动程序。

新原生更新器在包自检、激活指针前和前端启动前，读取受限构建记录、核对原生文件散列与
x64 架构，再检查系统目录中固定 VC DLL 的 FileVersion；不动态加载 DLL、不运行安装器。
依赖不满足时保留当前指针；pending 新版自检失败沿用既有上一版回退，上一版也必须经过
自己的检查。缺少 `vcRuntime` 的历史包返回“未知”并沿用旧包健康检查，不能称其依赖已通过；
存在但损坏的记录不会退回历史兼容路径。

旧更新器不会因为服务器发布新包就自动获得这段检查。原生更新器本身也依赖 VC++，
直接双击 EXE、旧版到新版的首次升级，以及缺失运行库的首次启动仍需原始 ZIP 引导或未来
正式安装器处理。这项工作没有宣称覆盖这些入口或通过真实安装验收。

脚本未签名时可能被本机执行策略阻止；入口不关闭或绕过执行策略。
签名安装器必须再处理受信引导入口，不能把这份预览脚本当作正式安装器完成。
二进制将来签名后散列会改变，需在正式签名流水线中建立“构建→签名→最终载荷”的可核对
记录；当前回执绑定未签名构建产物，签名后不能篡改回执绕过校验。

## 签名需要用户确认 / 提供

1. 正式发布者名称与采用的签名服务 / 证书类型；尚未配置 FUZE 发布者信任根。
2. 公开证书或证书 SHA-256 指纹及有效期，用于受信发布者约束和后续轮换设计。
   私钥、PFX 密码、令牌不要发到聊天或提交仓库。
3. 由用户在本机 / CI 的安全渠道安排硬件、云签名或证书访问授权，并确认时间戳服务。
4. 签名覆盖范围：FUZE EXE、引导脚本 / 正式安装器及更新侧发布者验证。
   微软和第三方 DLL 的有效签名不能代替 FUZE 自己的发布者身份。

拿到上述信息后才能确定正式签名接线；拿到证书也不等于干净机器、真实窗口、IME、
混合 DPI 或游戏同版本验收通过。正式稳定发布判断继续以这些独立证据为准。
