## 发现并处理的问题

1. PP-OCRv5 输出维度为 [1, T, 18385]，原型按 YAML 导出的 blank + 字符表只有 18384 类。按 PaddleOCR 的 use_space_char 规则在末尾追加空格；保留严格的输出形状检查，没有绕过不匹配错误。参见 [PaddleOCR 官方解码实现](https://github.com/PaddlePaddle/PaddleOCR/blob/main/ppocr/postprocess/rec_postprocess.py)。
2. 固定标题 ROI 两侧过宽会降低短标题置信度。新增 ROI 内的水平留白裁剪，去除卡框边带并保留上下文边距；保持 0.75 识别置信度阈值。该启发式仍须在更多布局、颜色及长标题上验证。
3. ORT 伴随 DLL 的查找目录只加到验证子进程的环境，不修改系统 PATH；阶段诊断只输出固定数字，原生库原始 stderr 不进入上传报告。
4. 原生窗口改为消费 OCR 契约快照，缺失卡位保留；不使用假胜率填充界面，不把识别结果当作选择界面确认或实际领取。

## 测量边界与后续门槛

模型初始化、一次预热、三槽识别分别计时。识别计时包含 ROI 处理、预处理、推理和匹配，不包含 PNG 文件解码、截图、IPC 和窗口显示；每张素材只跑三次。隐藏窗口的 500 ms 空闲采样不代表可见窗口或游戏中占用。

M0 只验证 CPU 固定标题识别和原生窗口接口。没有验证完整检测网络、多语言/多分辨率识别、GPU、原生游戏捕获、真实置顶与穿透、跨进程 worker 回收、实际领取轮次、安装迁移或差分更新。

M1 首先使用同设备、同 provider、同模型和输入做新旧链路对照，再验证原生捕获与 GPU 生命周期。最终 UI 框架仍待选型；Win32/GDI 原型不是最终主界面方案。未过这些门槛前继续保留现有稳定版和整体胜率推荐。
