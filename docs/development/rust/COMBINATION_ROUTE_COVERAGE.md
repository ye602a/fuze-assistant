# 第三批：路线覆盖与具体阶段对照

2026-11-15，接续已合并的 #231 / #234。应用是否包含本批，以主线提交和发布回执为准。

## 本批解决的问题

英雄组合榜单是有限的。没有进入当前英雄榜单的强化，之前只能显示“暂无对应记录”；
同时，多条已有路线只显示“另 N 条”，生产浮窗禁用点击后，其他目标实际上不可见。
四阶段反转也只有概括提示，没有说明相对哪张候选、在哪次选择出现差异。

现在卡面依次显示本英雄组合记录，或明确标注的跨英雄路线参考；增加第二条具名路线。
阶段说明明确绑定左／中／右候选，显示具体选择次数。推荐规则沿用第二批。

## 跨英雄路线只提供线索

`fuze_data::combination_routes` 从同一份已准备好的全量本地数据中读取各英雄的
`aramkitReference.augmentCombinations`。不新增统计 HTTP 请求，不接入另一种分段或数据源。

索引要求来源为 ARAMKit，英雄身份、补丁、日期及 dataPath 与 manifest 一致；
成员是该批资源中有效且启用的普通强化，包含 2–4 个不同 ID，原始胜率有效且样本至少 200 场。
这个 200 场条件用于筛选路线展示，不能代替本英雄情境比较的 500 场门槛。

每条索引只保存**组合成员和确实列出它的英雄 ID**，不保存或汇总胜率、场次、排名、推荐分。
同一英雄重复列出同一组合只计一次；来源英雄数量不是热度、选取率或组合收益。

显示时：

- 排除当前英雄，仅保留其他英雄确实出现过的记录。
- 当前英雄已有该候选的当前或后续组合记录时，继续优先显示该英雄记录。
- 当前英雄没有可用记录时，允许显示“跨英雄参考”，同屏注明“待本英雄验证”。
- 缺失成员较少的路线先显示，再按成员 ID 稳定排序；不按来源英雄数量排强弱。
- 已持有前置只改变缺失目标说明，不能让这条参考升级为本英雄组合胜率。
- 候选本身已持有、数据身份不一致、游戏补丁不一致时不显示；已过期英雄缓存也不借此恢复数值。
- 跨英雄结构与 `Snapshot.combinations`、`Candidate.current/future`、`HistoryContext` 分开，
  不参与 `Decision`、金框或“不建议”。

多个成员和长名称在卡面压缩并保留数量；完整成员及来源英雄 ID 保留在离线详情。
它仍然是有限榜单提供的线索，不能保证该组合对当前英雄有效，也不预测后续目标会出现。

## 旧数据可用，局内不扫描

不修改现有数据包、清单格式或更新版本判定。已有 ARAMKit 数据包含各英雄分片，
因此同一批旧缓存无需重新下载，即可在选人／加载准备时建立索引。

`stage_reference::Store` 缓存一份按数据身份、来源、清单及根目录集合区分的索引；
同一批次复用 `Arc`，缺失或不支持也记忆一次。复用原英雄准备结果中的名称与元数据，
首次索引构建才在后台从固定根目录读取 Full；局内 `CacheOnly` 不触发全表读取。
不同数据源不能在 Full 准备失败时悄悄互相补齐。

准备开始前、结束后和交付前检查 generation／准备许可。当前底层 Full 读取没有逐文件取消，
进入游戏会丢弃未完成结果，不能声称读取过程立即中断。索引缺失不影响原有英雄参考。

## 阶段对照说明

`stage_contrast(a, b)` 逐次复用原 `clear_order`：双方至少 500 场、差至少 2pp、
单项近似 Wilson 区间不重叠，才标出该次的比较方向。缺失、不足或差异不明确留空。

例如“对中卡：1/2优 · 3/4弱”表示同阶段两项历史记录的比较，不能解释为同一强化随时间变强或变弱。
说明优先采用决定中实际使用的阶段对手，否则优先反转，再取完整一致、有效阶段更多的对照；
最后按对手 ID 稳定选择。候选换位时，左／中／右标记同步改变。

四次全部明确同向才允许阶段比较参与推荐，这个规则不变。局部反转可以解释，但不猜当前轮次。
没有历史统计口径的情况明确标“口径未确认”，不把未知误称为已经证实的异批次。
实际正式领取轮次仍是 Unknown；公开事件来源的复核见 [领取信号验证](../../STAGE_SIGNAL_VALIDATION.md)。
